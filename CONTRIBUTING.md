# Check the evidence, then tell us what you found

We welcome corrections to the scoring, source reconstruction, interpretation and presentation. A useful report names a case or response ID, the claim at issue, the evidence that supports or contradicts it, and the command or reasoning needed to reproduce your result. Include the repository commit you inspected.

Run the README commands before proposing changes. Distinguish a recomputation of preserved responses from a fresh model run. For new inference, report the model artifact, configuration, prompts, selection and exclusions; do not pool it silently with the original data.

The experimental files under `study/` are preserved evidence; manuscripts and documentation may evolve with a recorded revision. Do not rewrite raw responses or labels to make a check pass. Submit a documented correction with before/after evidence and an explanation of which findings it changes. Keep negative results and counterexamples.

Do not upload credentials, private logs, personal data, model weights or source material without redistribution rights. Use synthetic examples for reporting tooling issues when possible. A GitHub issue or pull request is the normal route for non-sensitive corrections; do not post live security vulnerabilities or sensitive records in an issue.

## Propose a collaboration

For an exploratory conversation, email [research@fideai.org](mailto:research@fideai.org?subject=AI%20investigation%20evidence%20collaboration) with the question, the evidence or expertise you can contribute, and any constraints on sharing. Do not attach private logs or credentials.

Case proposals should identify source ownership and reuse terms, collection context, the proposed claim and the evidence needed to establish it. A source outcome and an answer justified by a limited input are different labels; explain both where possible. Several views of one event are not independent cases.

The present task already supplies a mechanically checkable rule. A useful review-method comparison should go beyond applying that supplied rule: qualify native logs, multi-record claims and unannotated missing fields. Include complete failures, complete successes, unresolved cases and an always-abstain baseline.

Method proposals should name the comparison, available evidence, computation budget, both kinds of error (unsupported conclusions and withheld justified conclusions), and a result that would count against the proposal. Freeze a new test before seeing its model outputs and keep it separate from the original ledger. New cases and runs are not automatically accepted into the study.
